# Benchmark Methodology

## Evidence boundary

The active v3 utility cohort is the committed Atlas billing service, Northstar developer
portal, and SignalForge telemetry distribution. They are original, seeded, and
byte-reproducible reference repositories with executable domain source, tests,
configuration, schemas, migrations, generated clients, stale documentation,
legacy surfaces, and operational decoys. This makes the comparison reviewable
and repeatable; it does not establish live-agent or live-model generalization.
Each versioned manifest embeds a sorted canonical inventory of POSIX paths and
exact content hashes. The aggregate tree hash, audit counts, owner evidence,
and regeneration check consume that inventory. Generated trees are committed
under `benchmarks/repos` so they can be inspected and reviewed directly; Git
preserves the generated bytes without checkout newline conversion and hashing
never normalizes content. Centrally recognized runtime cache directories are
outside fixture identity.

Maintained source is explicitly authored around application composition roots;
normalized source skeletons, nearest-neighbor shingle similarity, generated
content ratio, dependency connectivity, and source-inspection placeholder tests
are blocking quality checks. Python, TypeScript, Java, Go, Rust, and .NET native
build/test commands are enforced by fixture CI.

The flag-control-plane and subscription-platform fixture data remains available
for fixture-tool compatibility but does not contribute metrics or comparisons
to active v3 evidence.
`resolver-scale-stress` contains the former patterned 3k-file SignalForge corpus
and contributes only workload and phase-one latency results. Tier A repositories
remain smoke regressions. `realistic-large` remains at its
existing path as Tier D homogeneous-scale evidence: 206 of its 218 canonical
source-controlled files use a numbered pattern, so it is excluded from utility
claims. The initial 228-file worktree observation included ten ignored
`.ruff_cache` artifacts and is retained only as an audit correction.

## Fair conditions

Every condition receives identical task text and repository state.

- Resolver-first receives ranked phase targets, emitted fallback searches, and
  only source ranges supplied by the resolver.
- Ripgrep uses an independent lexical rank over `git ls-files` and `rg`, path
  and role heuristics, and the top three complete files. It does not import the
  resolver index or scoring helpers.
- Broad inventory receives tracked eligible source, test, and configuration
  inventory and complete eligible content where appropriate.

Prompts and answers live outside fixture repositories. Phase-aware ownership,
constraint, impact, and abstention rationale is stored in hash-bound external
oracle bundles. Owner claims are bound to file SHA-256 values and symbols.
Executable oracle tests are copied into a temporary repository only after
materialization. Network access is not needed for benchmark evaluation.

## Metrics and gates

The report records Hit@1, Hit@3, MRR, role precision/recall/F1, set-level owner
precision/recall, abstention precision/recall, incorrect high-confidence
targets, exact bytes and characters, offline `cl100k_base` tokens, patch
success, tokens per successful patch, failed-attempt tokens, and stable latency
budget outcomes. Incorrect resolutions receive no credited efficiency saving.

V3 utility gates retain strict safety and absolute balanced thresholds, then
require every machine-stable v3 evidence metric, workload count, and fixture
identity to match exactly:

- Hit@1 at least 0.85, Hit@3 at least 0.95, MRR at least 0.90;
- primary-owner precision at least 0.85, recall at least 0.80, and exact owner-set match at least 0.80;
- false-primary rate at most 0.10;
- constraint precision/recall at least 0.75/0.65 and impact precision/recall at least 0.70/0.60;
- macro role F1 at least 0.75;
- abstention precision and recall at least 0.90;
- no incorrect high-confidence target;
- resolver patch success non-inferior to both same-corpus controls;
- phase-one p95 under two seconds, build median under 30 seconds, refresh median
  under 15 seconds, and wall time within the greater of twice the calibrated
  cold run or 12 minutes representative / 30 minutes full.

Utility and scale phase-one P95 are reported separately and must each remain
under two seconds. Earlier corpus results are omitted: only controls executed
on the identical current v3 bytes are comparable.

## Patch simulations

Six canonical transforms are selected solely from the context supplied by each
condition. The harness then runs injected behavioral tests, checks changed
paths, and verifies protected paths. These are context-sufficiency simulations,
not model-performance evidence.

## Limitations

These original executable projects model technical repository structure but
omit social and organizational context found in production systems. The scale
fixture is deliberately synthetic and supports no quality or reliability claim.
Deterministic transforms do not model code generation.
Raw latency varies by machine, so the cold-run measurement sets a tolerant
ceiling while deterministic evidence excludes observed elapsed time from exact
comparison. The other skill portfolios
have not yet received fair baselines and outcome-specific comparative oracles.
